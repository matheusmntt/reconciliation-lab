# ADR 0003: Node 26 como runtime dos serviços Node

- **Status:** Aceita
- **Data:** 2026-10-01

## Contexto

Três serviços do projeto rodam em Node (gateway, integrações e conciliador), assim como os clientes TypeScript de `libs/sim-clock` e `libs/chaos`. O roteiro tem oito fases, e o runtime escolhido precisa continuar suportado durante todo esse período.

Calendário oficial de suporte das versões candidatas:

| Versão | Vira LTS | Fim do suporte |
| --- | --- | --- |
| Node 22 | 2024-10-29 | 2027-04-30 |
| Node 24 | 2025-10-28 | 2028-04-30 |
| Node 26 | 2026-10-28 | 2029-04-30 |

O domínio do projeto depende muito de datas e horários:

- todos os horários são guardados em UTC e convertidos para `America/Sao_Paulo` apenas nas bordas;
- liquidações em D+N (cartão em D+30 por parcela, Pix em D+0 ou D+1, boleto em D+1);
- data de competência da nota e prazo de cancelamento;
- a virada de dia por fuso horário faz parte do catálogo de caos.

O `Date` do JavaScript é mutável, não tem um tipo para datas sem horário e só conhece o fuso local e o UTC. O Node 26 traz a API Temporal habilitada por padrão (V8 14.6), com tipos distintos para instante (`Temporal.Instant`), data de negócio (`Temporal.PlainDate`) e data com fuso (`Temporal.ZonedDateTime`).

Alternativas consideradas:

- **Node 22**, já instalado: o suporte termina em abril de 2027, no meio do projeto.
- **Node 24**, LTS ativo: suporte até abril de 2028, mas sem Temporal habilitado por padrão.
- **Uma biblioteca de datas** (date-fns, Luxon) ou um polyfill do Temporal, em qualquer versão: mais uma dependência para resolver algo que o runtime já oferece.

## Decisão

Usar o Node 26 em todos os serviços Node e nas libs TypeScript.

- A versão é fixada no `.nvmrc` da raiz, e cada `package.json` declara `"engines": { "node": ">=26" }`.
- Apenas o binário oficial do Node é usado (nvm ou imagens Docker oficiais), porque o suporte a Temporal depende de como o Node foi compilado.
- O código de domínio usa Temporal para aritmética de datas e conversões de fuso. `Date` aparece apenas na fronteira com bibliotecas que o exigem.
- O "agora" vem sempre de `libs/sim-clock` (seção 8 do `project.md`). `Temporal.Now.*` e `Date.now()` não são usados no código de negócio, porque leem o relógio do sistema.
- Configuração TypeScript: `target` `ES2025` e `lib` `["ES2025", "ESNext.Temporal"]`, para tipar apenas o que o Node 26 oferece de forma estável. O `@types/node` é fixado na major 26 e o build usa `--target node26`.

## Consequências

### Positivas

- O runtime é suportado até abril de 2029, cobrindo o projeto inteiro sem migração de versão.
- Instantes, datas de negócio e datas com fuso têm tipos diferentes. Erros como confundir o dia em UTC com o dia em São Paulo ficam explícitos no código.
- Nenhuma biblioteca de datas é necessária.
- Os tipos do `@types/node` correspondem às APIs disponíveis no runtime.

### Negativas

- Até 2026-10-28 o Node 26 é uma versão Current, não LTS.
- O Temporal depende da build do Node. A build do Homebrew, por exemplo, é compilada sem ele (`v8_enable_temporal_support=0`). As imagens Docker usadas precisam ser verificadas, especialmente as variantes Alpine, que são builds não oficiais.
- Drivers e ORMs (`pg`, Drizzle) trabalham com `Date` ou strings. É preciso uma camada de conversão na fronteira da persistência.
- O Temporal é recente, e há menos material e exemplos disponíveis do que para `Date`.
- O Node deixou de distribuir o Corepack a partir da versão 25, então o gerenciador de pacotes é instalado separadamente ([ADR 0004](0004-pnpm.md)).
