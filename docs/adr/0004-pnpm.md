# ADR 0004: pnpm como gerenciador de pacotes

- **Status:** Aceita
- **Data:** 2026-10-01

## Contexto

Cada serviço Node é independente, com dependências e lockfile próprios, e não há workspaces entre serviços ([ADR 0001](0001-monorepo.md)). O alvo `install` do contrato instala as dependências exatamente como estão no lockfile ([ADR 0002](0002-makefile-como-ponto-de-entrada.md)).

O projeto simula um ecossistema financeiro, e a cadeia de dependências é uma superfície de ataque real. Por padrão, o npm executa os scripts de instalação de qualquer dependência e resolve versões no instante em que são publicadas, que é justamente a janela explorada por pacotes comprometidos.

A partir da versão 11, o pnpm traz proteções ativadas por padrão:

- `strictDepBuilds`: a instalação falha se alguma dependência tiver scripts de instalação não autorizados;
- `minimumReleaseAge` de 1 dia: versões publicadas há menos de 24 horas não são resolvidas.

Além disso, o pnpm monta um `node_modules` estrito, em que só as dependências declaradas podem ser importadas, e guarda os pacotes num store global endereçado por conteúdo.

O Node deixou de distribuir o Corepack a partir da versão 25 ([ADR 0003](0003-node-26.md)). Seja qual for a escolha, um gerenciador diferente do npm precisa ser instalado à parte.

## Decisão

Usar o pnpm em todos os serviços Node e nas libs TypeScript.

- A versão é fixada por serviço no campo `packageManager` do `package.json` (por exemplo, `pnpm@12.8.1`). Se outra versão estiver instalada, o pnpm baixa e usa a versão declarada.
- Cada serviço tem um `pnpm-workspace.yaml` próprio, usado **apenas para configurações**, porque o pnpm não lê mais o campo `"pnpm"` do `package.json`. O arquivo não declara `packages`, então não agrupa serviços. Ele também interrompe no diretório do serviço a busca do pnpm por uma raiz de workspace.
- As proteções padrão são mantidas. Toda dependência autorizada a rodar scripts de instalação é listada explicitamente em `allowBuilds`. Hoje a única é o `esbuild`, usado pelo `tsx` e pelo `tsup`.
- O alvo `install` dos Makefiles usa `pnpm install --frozen-lockfile`.
- O lockfile (`pnpm-lock.yaml`) é sempre versionado.

## Consequências

### Positivas

- Há proteção contra ataques na cadeia de dependências sem configuração adicional: nenhum script de dependência roda sem autorização, e versões recém-publicadas esperam 1 dia.
- O `node_modules` estrito impede importar pacotes não declarados, o que reforça a regra de que cada serviço só usa o que declara.
- Os serviços compartilham o store global de pacotes, o que economiza disco e acelera instalações.
- A versão do gerenciador é reproduzível, porque fica registrada em cada serviço.

### Negativas

- O pnpm é mais uma ferramenta a instalar. Com o nvm, ele precisa ser instalado em cada versão do Node.
- O nome `pnpm-workspace.yaml` sugere um workspace, mas aqui o arquivo só guarda configurações. Esta ADR e um comentário no próprio arquivo explicam isso.
- Toda nova dependência com scripts de instalação quebra o `install` até ser avaliada e adicionada ao `allowBuilds`. Essa fricção é intencional.
- A idade mínima de release atrasa em 1 dia o acesso a correções urgentes, a menos que a configuração seja ajustada no `pnpm-workspace.yaml`.
- As imagens Docker precisam instalar o pnpm explicitamente, na versão declarada em `packageManager`, porque o Corepack não vem mais com o Node.
